# PWA QR Pairing

## Problem

On iOS, opening the generated pairing link launches Safari rather than an installed home-screen web app. The secure cookie is therefore created in Safari's browser context, while the standalone app remains unauthenticated.

## Design

The unauthenticated pairing screen adds a **Scan QR code** action. It opens a full-screen rear-camera scanner inside the current PWA using `getUserMedia`. Because iOS Safari does not enable `BarcodeDetector`, a small QR decoder is bundled with the web UI and processes reduced-resolution video frames locally.

A decoded value is accepted only when it is an HTTPS URL for the current origin containing a syntactically valid `#pair=` token. The app passes that token to the existing `POST /api/auth/exchange` endpoint, receives the existing secure cookie, closes the camera, and loads the protected UI without navigation.

A **Paste pairing link** fallback supports camera denial and accessibility needs. Camera tracks stop on success, cancellation, page backgrounding, and component teardown. Errors remain in the scanner for retry; expired or consumed tokens use the server's existing error response.

## Security

- QR images and camera frames never leave the device.
- The scanner does not navigate to decoded URLs.
- Pairing URLs must be HTTPS and same-origin.
- Token syntax and server-side single-use/expiry checks remain unchanged.
- No server/auth protocol changes are required.

## Verification

- Unit-test same-origin token extraction and rejection cases.
- Unit-test the bundled decoder against a QR generated by `server/qr.js`.
- Browser-test camera-sheet lifecycle and same-window authentication.
- Run `npm test`, `npm run check`, and `npm run build`.
